给视觉 Diffusion Policy 加一个接触先验：实验记录

一、从一个假设说起

LeRobot 里的视觉版 Diffusion Policy 在 PushT 任务上的输入很简单：一张 96×96 的 RGB 图像，加上 agent 的二维位置，输出未来一段时间的动作序列。图像里其实已经隐式包含了 agent 有没有碰到 T 形块这个信息——只是策略网络得自己从像素里把这个关系学出来。

我想验证的问题是：如果把”是否接触”这个信息以显式特征的形式直接提供给策略，会不会降低学习这层关系的难度，从而在样本效率或成功率上带来提升。

需要先说清楚一件事：这里的”接触信号”不是真实的触觉传感器读数，而是根据 agent 和 T 形块的几何关系算出来的一个代理信号。整篇文章里我会一直用”几何接触先验”这个更准确的说法，避免让人误以为这是一次真实的触觉集成实验。

提前说结论：这次实验证明了一条完整可用的工程链路，但没有证明接触先验本身有效——不是因为它被验证无效，而是因为现在的证据强度还不足以支持任何一个方向的结论。原因会在后面几节慢慢展开，其中训练配置核实和评估结果这两节的发现是我最初没预料到的。

二、Diffusion Policy 概览：从观测到动作序列

在动手改造之前，有必要先把 Diffusion Policy 本身的机制过一遍。

策略网络接收最近几步的观测（图像经过视觉编码器、加上本体状态），把它们编码成一个条件向量。训练时，从数据集里取一段真实的动作序列，随机选一个扩散时间步，按 DDPM 的加噪公式把这段序列加噪，网络的任务是去预测加进去的那份噪声，条件向量通过 FiLM 层调制网络中间层。这本质上是把 DDPM 从”给图像去噪”搬到了”给一段动作序列去噪”。

推理时反过来：从纯高斯噪声出发，反复调用网络做反向去噪，迭代若干步后得到一段预测的动作序列。执行时并不会把这段序列全部跑完——只执行开头的一小部分，然后拿新的观测重新走一遍整套流程，这种”receding horizon”的执行方式让策略既能利用长序列规划的稳定性，又能对新的观测保持反应能力。

这也是接触先验要插入的位置：它不改变去噪目标本身，只是给条件向量多提供一维信息，理论上让模型更容易判断”什么时候该开始精细调整”。

三、构造接触先验：两个数据集、八个关键点

LeRobot 官方提供的 lerobot/pusht 数据集只有图像和二维 agent 位置，没有 T 形块的几何信息，没法直接算接触信号。好在还有一个 lerobot/pusht_keypoints 数据集，提供了对齐的 16 维 observation.environment_state，也就是 T 形块的 8 个二维关键点。

先验证了一件容易被忽略的事：两个数据集是不是同一批演示数据的不同导出版本——按 frame index 对齐后确认样本 0 的 agent state 完全一致，才敢放心地逐帧拼接两个数据集的信息。

T 形块由两个矩形拼成，8 个关键点按前 4 个、后 4 个分别构造成两个矩形。接触信号的定义是 agent 圆心到这两个矩形的最近欧氏距离，取两者中较小的一个：

15.5 这个阈值来自 agent 半径 15，加上 0.5 的安全余量。用二值信号的好处是语义清楚，代价是丢掉了距离的连续信息，也引入了阈值本身是否合理这个新的不确定性——这个后面会再提一句。

四、把 observation.state 从二维扩展到三维

算好逐帧的接触信号之后，把它拼接到原来的二维 observation.state 后面，保存成一份本地 LeRobot 数据集。这一步最省心的地方是：LeRobot 会从数据集的元信息里自动推导 observation.state 的输入维度，不需要去改 DiffusionConfig 的源码，训练脚本对二维还是三维输入是无感的。

图像输入本身没有变化，改动完全在状态向量这一侧，这样能保证对照实验里唯一变化的变量确实只有这一维接触信号。

五、训练和在线评估之间的一致性问题

这是整个项目里工程量最大的一部分。离线训练时接触信号是逐帧算好、拼在数据集里的，但在线跑仿真评估时不是这样——环境每一步吐出来的原始观测里只有 pixels 和 agent_pos，没有 T 形块的几何信息。

info 字典里倒是有一个 block_pose，一开始想着直接用它自己重建关键点，但很快发现更稳妥的做法是复用环境本身提供的 get_keypoints 接口——它和数据集里的关键点定义是同一套坐标系统和顺序，自己重建反而更容易在坐标系或点的排列顺序上出错。

最终方案是写一个 gym.Wrapper，在 reset 和每次 step 之后调用 get_keypoints 拿到当前 T 形块的关键点，复用和离线训练完全相同的几何计算函数，把结果追加到 agent_pos 后面，同时把 observation_space 里 agent_pos 的维度声明从 2 改成 3。这个方案没有改动 gym_pusht 或 LeRobot 主仓库任何代码，实验改动完全隔离在自己的 wrapper 里。

这一节想强调的经验是：训练和在线评估其实是一套接口契约，特征的维度、语义、关键点顺序、阈值这些必须两边完全一致，任何一处悄悄分叉，模型看到的分布就变了，而这种偏差往往不会直接报错，只会安静地拖累效果，很难第一时间意识到。

六、调试笔记：几个值得记的坑

preprocessor / postprocessor 和归一化的关系——训练时会在数据集上算出每个 key 的统计量（均值方差或 min/max），存进 checkpoint。新版 LeRobot 把”改 key 名、加 batch 维、搬设备、按统计量归一化”这一串操作封装成 preprocessor，把”策略输出的动作从归一化空间转换回真实坐标尺度”封装成 postprocessor。这两个不是可选的便利功能，而是模型输入输出的契约本身。跳过它们最直接的后果是：agent 会被输出的动作拉到画面之外的负数坐标——因为模型的输出其实一直停留在归一化空间，没有被正确地转换回真实尺度。

看起来像真值的字段不一定是真值——排查过程中一度想直接用环境里一个叫 n_contacts 的字段作为标签来源，后来发现它的语义并没有隔离到”agent 和 T 形块”这一对具体关系上，不适合直接当作接触判定的真值，改用自己按几何关系显式计算的方式更可靠。

checkpoint 路径要每次核对——在多个训练版本、多个 step 之间切换评估脚本时，很容易在复制粘贴命令时漏改路径，评估了错误的 checkpoint 却浑然不觉。这个坑很低级，但发生频率不低，值得养成每次运行前打印一遍实际路径的习惯。

七、评估协议：怎么避免被噪声带偏结论

第一版评估脚本只跑了单个 episode，看着 agent 完成了任务，很容易就想得出”接触信号有效”的结论。但单局成功只能说明链路能跑通、行为合理，不能替代成批对照——不同初始条件下同一个模型的表现本身就有很大方差。

批量跑之后发现问题更明显。用 20 个 episode 对比 baseline 和接触版本，两次实验里谁更好这个结论完全不稳定：一次是接触版本成功率更高，另一次接触版本的平均 reward 反而更低。这不是巧合，而是样本量太小导致的必然结果——在真实成功率在 15% 附近时，20 个 episode 下成功率的 95% 区间宽达 ±15 个百分点左右，也就是说观测到的差异基本完全落在噪声范围内，不能用来支持任何结论。

更准确地说，这个区间不是频率学派意义上的置信区间，而是贝叶斯的 Beta 后验可信区间：把”完全无偏好”的 Beta(1,1) 先验，结合观测到的 k/n 成功次数，更新成后验分布 Beta(k+1, n-k+1)，再从这条后验密度曲线上切出中间 95% 的面积对应的成功率范围。它比传统置信区间更适合小样本下的成功率估计——天然限制在 [0,1] 之间，且不需要多次重复实验去”画曲线”，一次 eval 的 k 和 n 就足以完整确定整条后验曲线。判断两个模型是否有真实差异的实用标准很直接：把两组的后验区间摆在一起，如果大幅重叠，就说明现有数据不足以支持”两者有差异”这个结论。

评估协议里另一个容易被忽视的细节是 seed。这里其实有两层完全不同的东西：

训练时设置的 seed，控制的是权重初始化、数据打乱顺序、以及扩散过程里噪声和时间步采样这一整条随机数消耗序列的起点。看起来给 baseline 和接触版本设置同一个训练 seed 就能让两次训练完全可比，但接触版本因为输入多了一维，网络第一层的参数形状不同，仅仅是初始化这一步要消耗的随机数数量就和 baseline 不一样，后面数据打乱和噪声采样也就跟着错位了。所以训练 seed 相同只能减少一部分差异带来的噪声，没法做到完全对齐。

评估时的 seed 是另一回事——env.reset(seed=ep) 控制的是仿真环境自己的随机数生成器，只用来决定这一局的初始局面（T 形块和 agent 的起始位置），和策略网络内部的随机性完全独立，不会受模型结构差异影响。所以固定评估 seed 才是真正精确的对齐：只要用同一串 seed，两个模型面对的就是完全相同的一组初始局面，这才是能拿来做公平对比的部分。

最终的评估协议定下来是：baseline 和接触版本用完全相同的一串 seed 跑仿真环境，训练超参、图像输入、最大 rollout 步数全部保持一致，唯一有意改变的变量是那一维接触信号；结果同时报告成功数除以总局数（success_rate）和所有 episode（含失败）的平均连续覆盖率分数（avg_reward）——后者比二值化的 success_rate 更细粒度，能看出”虽然都没成功，但谁推得更接近目标”这类信息，两个指标合起来看，比只看一个更不容易被单一指标的噪声误导。

八、训练规模核实：一次比想象中更彻底的返工

第七节解决的是”怎么公平地比较两个模型”，但这一节要交代的是一个更基础的问题：在开始纠结比较方法之前，这两个模型本身是不是都训练充分了？

答案是否定的，而且差距比最初以为的更大。

先从 loss 曲线的一个误导性信号说起。 早期训练的 train/loss 曲线在不到 1000 个 step 就从初始值快速下降，之后一路到一万多个 step 都停留在一个很平坦的区间，几乎看不出再下降。这个现象本身很容易被解读成”模型已经学得差不多了，继续训大概率是浪费算力”——我一度也是这么想的。

直到把这条曲线和 LeRobot 官方自己公开的 lerobot/diffusion_pusht 训练日志放在一起看，才发现这个直觉是错的。官方训练的 loss 同样在 2 万到 3 万个 step 左右就基本走平，之后一直到 12 万步都稳定在 0.01～0.03 这个区间，几乎没有肉眼可见的进一步下降。但把同一批 checkpoint 拿去做 rollout 评估，success rate 在 loss 完全看不出变化的这十几万步里，从 10k 步时的 12% 一路爬升到 150k～200k 步时稳定在 60%～74% 的区间，中间还有不小的波动（比如 120k 步一度回落到 58%）。

这说明 train/loss 衡量的是”预测噪声这个局部回归任务准不准”，网络很快就能学到这一点；而 success rate 衡量的是”整段去噪迭代 + receding horizon 闭环执行之后，动作序列能不能真正完成任务”，这是一个粒度完全不同、收敛速度也慢得多的信号。loss 走平不代表策略行为已经收敛，这是这次核实过程里最有价值的一个纠偏。

再看训练配置本身的差距。 把自己的训练命令行和官方仓库里公开的 train_config.json 逐项核对之后，发现的差距比之前预估的更大：

  • batch_size：官方配置是 64。而这次实验的训练命令里没有单独指定这个参数，走的是框架默认值——经核实后确认默认值是 8，而不是最初以为的 32。同样的 step 数下，实际处理的数据量差距被严重低估了：80000 步 × batch_size 8 ≈ 64 万条样本，相比官方 200000 步 × batch_size 64 ≈ 1280 万条样本，实际训练量大约只有官方的 **5%**，而不是最初粗算的 20%。
  • steps：这次实验只训到了 80000 步左右，是官方 200000 步目标的 40%，叠加上面 batch_size 的差距，两者共同作用后差距被明显放大。
  • 图像增强和 EMA：这是最反直觉的一处核实结果。最初设想的排查方向是”官方大概率开了这两项，而这次实验没开，所以有差距”——但直接查证官方 train_config.json 后发现完全相反：image_transforms.enable 字段的值是 false，官方基准训练时图像增强其实是关闭的；配置文件里也完全没有 use_ema 或同类字段，说明这个官方基准模型本身没有使用 EMA。也就是说，这两项此前设想中的”待核实差距”根本不存在，真正的差距完全集中在 batch_size 和 steps 这两项数据吞吐量相关的参数上。

这个核实过程带来一个实际的方法论提醒：排查训练差距时，”猜测官方用了更复杂的技巧”是一种容易走的弯路，直接去查官方公开的配置文件，往往比凭直觉补全设置更可靠、也更省时间。

基于这个核实结果，目前正在做的是：把 batch_size 改成 64、steps 目标改成 200000，图像增强和 EMA 都保持关闭（对齐官方而不是过度设计），重新训练 baseline 和接触版本。由于中途在 100k 步左右保存过 checkpoint，训练是通过 LeRobot 的 --resume=true 机制在原有 optimizer 状态和数据读取顺序基础上继续跑向 200k，而不是从头重新训练。

九、100k 步节点的阶段性评估：为什么现在还不能下结论

在等待训练跑满 200000 步的过程中，用当前 100k 步左右的 checkpoint 各做了一轮阶段性评估，权当中途检查点，而不是最终结论。

两组独立评估的结果如下（成功率 / avg_reward）：

baseline contact
n=100 37% (37/100), avg_reward 116.39 37% (37/100), avg_reward 109.25
n=50 42% (21/50), avg_reward 110.68 28% (14/50), avg_reward 120.30

单看数字会觉得有点矛盾：第一组两者成功率打平，但 baseline 的 avg_reward 更高；第二组 success_rate 上 baseline 明显领先，avg_reward 却反过来是 contact 更高。把这几组数字换算成 Beta 后验区间就能看清这个”矛盾”是怎么回事：

即使把两次评估合并成一组 150 episode 的估计，baseline 的区间是 [0.31, 0.47]，contact 的区间是 [0.27, 0.42]，两者依然有大段重叠（0.31～0.42）。这个重叠意味着，现有数据完全不足以说明这两个模型之间存在真实差异——两组数字之间”谁更好”的摇摆，本质上就是小样本噪声的正常表现，而不是接触先验在起作用或者起反作用的信号。

这个结果本身并不意外，反而印证了第八节的核实结论：100k 步、batch_size 64 的这一轮，仍然只是刚好达到官方训练量的一半左右（100000 × 64 = 640万 vs 官方 1280万），而且从第八节官方曲线里 100k～150k 这个区间的 success rate 走势看，这正是数值本身仍在波动上升、还没有完全稳定下来的阶段。在这个训练进度上做出”两者有没有差异”的结论，为时尚早。

真正能拿来做决定性对比的评估，需要等训练跑到 200000 步附近再进行——那时候两个模型的能力上限才真正对齐了官方验证过的训练规模，观察到的差异（如果有的话）才更有可能反映接触先验本身的效果，而不是训练本身还没收敛这个更大的干扰因素。

十、目前能负责任地说什么

工程链路是完整且可复用的：数据构建、维度扩展、在线一致性接入、评估协议设计这几块都经受住了检验，也梳理清楚了一套具体可操作的评估方法论（Beta 后验区间判断重叠、区分训练 seed 和评估 seed 的不同作用、success_rate 和 avg_reward 互相印证）。

不能说的是接触先验是否真的有效。100k 步节点的阶段性结果显示两者的表现区间大幅重叠，但这个节点本身的训练规模还没有对齐官方验证过的设置，不足以把”接触先验有没有用”这个问题从”训练本身是否收敛”这个更大的干扰因素里剥离出来。

这和最初设想的”跑几组对比就能有答案”不一样，但把这个边界看清楚——包括中途纠正了对 loss 曲线、对官方训练配置的两处误判——本身也是这次实验里最有价值的产出之一。

十一、后续方向

  • 等 baseline 和接触版本都训练到 200000 步附近，用固定的一组评估 seed（更大样本量，比如 200～500 episode）重新做一轮对比，这次的结果才具备下结论的资格。
  • 把二值接触信号换成连续距离或者软阈值形式，保留更多几何信息，也降低阈值本身设定是否合理这个额外的不确定因素。
  • 在多个训练 checkpoint（比如 20k、50k、100k、150k、200k）上用同一组 seed 做评估，画出样本效率曲线，直接回答”是否学得更快”而不只是”最终是否更好”这个问题——第八节里官方曲线本身波动不小，接触先验会不会让这条曲线更平滑、更早收敛，也是一个值得单独观察的维度。
  • 探讨这个几何代理信号和真实触觉传感器读数之间的差距，为以后往真实触觉信号迁移做准备。
