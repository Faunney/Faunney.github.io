【项目笔记】OpenGaussian改造设计

Created2026-05-14|Updated2026-09-16|项目笔记
|Word Count:2.5k|Reading Time:8mins|Post Views:

论文是做什么的

OpenGaussian（NeurIPS 2024）解决的问题是：给定一个 3D 场景，能不能用自然语言查询找到对应的物体，并精确定位到 3D 点级别。

这个问题以前也有人做，但大多数方法是在 2D 像素级别做语义理解，3D 只是顺带的。OpenGaussian 的出发点是：直接给每个 3D Gaussian 关联一个语义特征，这样查询结果天然就是 3D 点级别的，不需要从 2D 反投影。

场景表示用的是 3D Gaussian Splatting（3DGS）。3DGS 把场景表示成一堆椭球形的高斯球，每个球有位置、颜色、透明度等属性，渲染速度很快。OpenGaussian 在每个高斯球上额外加了一个实例特征向量，用来区分不同物体。

方法：四个阶段

整个训练流程分四个阶段，逻辑上是递进的。

Stage 0：标准 3DGS 预训练。 先把 RGB 渲染质量训好，30000 步，不涉及语义特征。

Stage 1：连续实例特征学习。 开始给每个高斯球训练 6 维实例特征。监督信号来自 SAM 分割出的 2D mask——同一个 mask 内的像素特征应该相近（cohesion loss），不同 mask 之间的特征应该尽量远离（separation loss）。这一阶段训出来的特征是连续的，还没有离散化。

Stage 2：两级 Codebook 离散化。 把连续特征量化成离散的 cluster ID。先做粗粒度聚类（k1 个 root cluster），再在每个 root 内部做细粒度聚类（k2 个 leaf cluster）。最终每个高斯球有一个 leaf cluster ID，空间上相近且特征相似的点会被分到同一个 cluster。

Stage 3：2D 语言特征关联。 训练结束后，把每个 3D leaf cluster 和 2D SAM mask 做关联，把 mask 对应的 CLIP 语言特征聚合进来。推理时，把文本编码成 CLIP 特征，和每个 cluster 的语言特征做 cosine similarity，找最相似的 cluster 渲染出来，就是查询结果。

Stage 3 是一个 training-free 的后处理步骤，不影响前面的 3DGS 参数，但对最终检索质量影响很大。

Baseline 结果

在 ramen 场景上跑 OpenGaussian 的文本选物体流程，整体结果是：mIoU = 0.2027，Acc@0.25 = 0.2958，Acc@0.5 = 0.1690。只看总分很难判断问题出在哪里，把结果按 query 拆开统计：

两个比较明显的现象：第一，有些目标能稳定生成预测且 IoU 较高，例如 nori 和 chopsticks。第二，有些目标虽然能生成预测但 IoU 很差，例如 corn 和 onion segments；还有一些目标经常无法生成预测，例如 glass of water、plate 和 sake cup。

失败模式

结合原图、SAM mask 和最终的 silhouette 结果，失败大致分成两类。

第一类是小目标、碎片化目标，典型例子是 corn 和 onion segments。这些目标本身很小，和周围食材混在一起，SAM 很难稳定地把它们分成独立实例。上游伪标签不干净，后面的 3D 聚类和文本匹配基本也很难恢复出正确目标。

第二类是 2D 上已经有候选区域，但 3D 检索仍然不稳定，典型例子是 sake cup 和 glass of water。这类目标在 SAM mask 里并不是完全没有分出来，但最终仍然经常没有生成预测结果。这更像是文本 query 和正确 3D cluster 没有对上，而不只是上游分割的问题。

OpenGaussian 的问题并不只在 3D 表示本身，而是同时受制于上游 mask 质量和文本检索鲁棒性，这两类问题的解决思路是不同的，需要分开看。

改动一：Multi-prompt 融合匹配

基于上面的观察，先做了一个轻量的尝试：把推理脚本里的单提示词匹配改成多提示词融合匹配。不只用 sake cup 这一个词，而是把若干近义 prompt 的文本特征先平均融合，再与 3D cluster 做 cosine 匹配。

这个改动没有动训练过程，想验证的问题很简单：有些失败是不是只是因为 query wording 太脆弱？

结果

指标 Baseline Multi-prompt 变化
mIoU 0.2027 0.2612 +0.0585
Acc@0.25 0.2958 0.3662 +0.0704
Acc@0.5 0.1690 0.2394 +0.0704

具体类别的变化更值得看：

Query Baseline Multi-prompt
sake cup 6 次中成功预测 3 次，平均 IoU 0.0002 6 次中成功预测 6 次，平均 IoU 0.6925
glass of water 2 次中成功预测 0 次 2 次中成功预测 2 次，但 IoU 仍为 0
nori 6 次，平均 IoU 0.7713 6 次，平均 IoU 0.7713，基本无变化
chopsticks 7 次，平均 IoU 0.6155 7 次，平均 IoU 0.6155，基本无变化

改动主要改善的是低检出类别。sake cup 在 baseline 里有一半的帧根本没有输出预测，不是 IoU 低的问题，而是系统直接放弃了这个 cluster。multi-prompt 让它在所有帧都能生成预测，平均 IoU 从 0.0002 涨到 0.6925，说明对应的 3D cluster 其实是存在的，只是 sake cup 这个词没有精确命中它。glass of water 虽然 IoU 仍然是 0，但从”完全没有预测”变成了”能够生成预测”，问题性质已经从”找不到”变成了”找到了但不够准”。

这个改动本质上是 prompt-level 的 hack，能说明系统对 query wording 是敏感的，但依赖人工理解和手工补词，不够通用。

改动二：Stage 3 软匹配

接下来把注意力转向 train.py 里真正影响 3D cluster 语言特征质量的部分——Stage 3 的 2D mask 到 3D cluster 关联过程。

原版的关联逻辑是硬阈值匹配。对于每个 leaf cluster 在每个训练视角里，计算它与所有 SAM pseudo mask 的联合得分（IoU × 特征相似度），取最高分的那个 mask 作为匹配结果：

丢弃之后，这个视角对该 cluster 的语言特征没有任何贡献。最终每个 cluster 的语言特征是所有匹配视角的简单等权平均。

对于小目标或视角不佳的帧，3D cluster 和 2D mask 的对齐本来就不会很好，得分低于 0.2 很正常，但并不代表这个视角完全没有信息。一刀切丢弃会让这些 cluster 的语言特征只由少数几个视角决定，稳定性差。

改动

把硬阈值改成双阈值软匹配：

score ∈ [0.05, 0.2) 的视角不再直接丢弃，而是按 score 大小加权参与语言特征的累积。score < 0.05 的才真正丢弃。最终每个 cluster 的语言特征变成加权平均，置信高的视角权重大，弱匹配视角贡献小但不为零。

结果

指标 Baseline Multi-prompt 软匹配（train 改动）
mIoU 0.2027 0.2612 0.3379
Acc@0.25 0.2958 0.3662 0.4648
Acc@0.5 0.1690 0.2394 0.3803

mIoU 从 0.2027 涨到 0.3379，比 multi-prompt 的 0.2612 还高出不少。render 端用的是和 baseline 一样的原版，两个改动是完全独立的。

受益最明显的是那些在 baseline 里对齐得分偏低、容易被硬阈值过滤掉的目标，比如 sake cup、bowl、napkin。软匹配让它们在更多视角里积累了有效的语言特征，检索时更容易被正确命中。

得分在 0.05~0.2 之间的视角并不是”匹配完全错了”，只是对齐不够完美，仍然提供了一定的正确信号。原版直接丢掉这部分，等于在信号本来就稀疏的 cluster 上进一步加大了噪声。让得分本身充当权重，在信号稀疏的情况下是更合理的策略。

完整消融汇总

版本 train render mIoU Acc@0.25 Acc@0.5
Baseline 原版 原版 0.2027 0.2958 0.1690
Multi-prompt 原版 多提示词融合 0.2612 0.3662 0.2394
软匹配 软匹配 原版 0.3379 0.4648 0.3803

两个改动相互独立，分别作用在推理端和训练端。两者同时开启的组合效果尚未测试。

总结

Baseline 的问题同时来自两个方向：推理端的文本 query 对措辞敏感，训练端的 2D-3D 关联因为硬阈值丢掉了太多弱但有效的匹配信息。multi-prompt 是在推理端打补丁，软匹配是在训练端改机制，后者的提升幅度更大也更根本。

还有一类问题这两个改动都没有解决：corn、onion segments 这类小目标，上游 SAM 就已经分不好，后面怎么改匹配逻辑都很难救回来。伪标签质量和小目标处理是后续值得单独看的方向。
